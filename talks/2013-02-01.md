title: "Process Algebra for Better Mocking"

Suppose you have a software component A which depends on some other component B and you want to test A but don't have access to B. The common approach to dealing with this is to write some piece of code which can act as replacement for B for the purpose of testing. Writing replacement code for testing purposes is referred to as "mocking".
There is no shortage of libraries to help write mocking code. But these libraries typically don't have a specified semantics: the implementation is the semantics. As usual in situations like this, the mocking libraries can exhibit very non-intuitive behaviors because they lack a well-thought-through semantics. Furthermore, the expressiveness of these libraries is often unclear and hard to gauge.

We present a clear an expressive semantics for mocking based on process algebra. Certain mocking specifications in our language can give rise to ambiguities and for this reason we have developed a sound and complete analysis which is used to reject ambiguous specifications. We will also sketch how to implement this semantics efficiently.

We have used a precursor of this work when testing AUTOSAR components.
